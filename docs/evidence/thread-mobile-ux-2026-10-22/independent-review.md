## Follow-up findings resolved in the final source

1. **P1 — Revisiting an older composer after a second submission could reuse an already committed key and erase a new reply.** Original follow-up locations: `public/assets/composer.js:934–937,1027–1033,1041–1054`. `rememberPendingDraftSubmit` replaced the previous record for a draft key/context. Send A under K1, then B under K2 in the same topic: the record for completed K1 disappeared. Back to the older pre-A entry restored K1, but reconciliation saw only K2 and did not rotate K1. Editing C also did not rotate, so submission replayed A and cleared unsent C. The original extracted-function reproduction produced `{"currentBody":"C","currentSubmission":"older-committed-K1","knownLatest":"latest-committed-K2"}`. **Resolved:** the journal is now keyed by submission identity and retains 20 entries; fresh mounts do not import unknown tokens. Retained/BFCache instances also run `rotateEvictedSubmission` during restore and before submit, using `_rbLastSubmittedToken` to identify actual prior submissions that have fallen out of the journal. A final-source extracted-function reproduction with the actual retained-instance marker and 20 later entries produced `{"journalLength":20,"body":"New work C","key":"fresh-token"}`. The new real-browser two-send/two-Back case passed on mobile in the inspected 24-case run; its desktop counterpart was blocked by the fixture's posting limiter in that run.

2. **P2 — The late-autosave guard missed multiline drafts because wire newlines differ from JavaScript editor newlines.** Original follow-up locations: `public/assets/composer.js:760–767,890–893`; persistence: `src/Controller/DraftController.php:50–57`. Exact pending/server body comparison failed because multipart FormData changes LF to CRLF while the controller stores raw POST body. A read-only serialization experiment produced `{"pendingBody":"line one\nline two","wireBody":"line one\r\nline two","exactMatch":false}`; no request was sent. **Resolved:** `sameDraftBody` normalizes CRLF/CR to LF and is used for metadata-bound remote suppression, history reconciliation, and matching local cleanup. Executing the final helper against those two bodies returned `true`. The new browser late-multiline-autosave case passed on mobile in the inspected 24-case run; its desktop counterpart was blocked by the posting limiter.

3. **Additional checks — Journal eviction and dock/header stacking.** The retained-instance journal-eviction gap described above was reproduced before the final `rotateEvictedSubmission` addition and no longer reproduced afterward. The dock initially used `z-index:40`, equal to the header's `--z-chrome:40`; because the dock occurs later in the document, its stacking context could paint above the header's account dropdown. The final dock now uses `calc(var(--z-chrome, 40) - 1)`, above post toolbars at 30 and below header chrome at 40. This stacking resolution is verified from source; no new browser hit test was run by this reviewer.

## Original findings resolved in the second-pass source

1. **Original P1 — Editing after an uncertain committed submission reused its key.** The new implementation compares the full editable payload on adapter/input/change events, during restore, and immediately before recording submission. The browser case “rich history cleanup preserves a newer draft in another tab after settling” passed in `browser-recovery-debug.txt`. Repeating the extracted-function async-adapter reproduction against current source retained local draft B after settlement: `{"body":"","key":"rotated-key","local":"B"}`.

3. **Original P2 — Body-only matching cleared a fresh same-text draft.** Completion matching now requires the current history entry's submission token, and remote suppression requires metadata submission identity as well as body. The extracted current-function same-text check retained body A and its new key. The 20-case browser run also passed both desktop/mobile “a later draft may deliberately repeat a confirmed reply” cases. The separate CRLF comparison issue is resolved above.

4. **Original P2 — Compact-byline flattening also affected staff removed-post stubs.** `public/assets/app.css:11595` now scopes `display: contents` to `.post:not(.post-deleted) > .post-main`. The deleted stub consequently retains its original wrapper and stacked contents. This is source verification; this reviewer did not run a browser or inspect a dedicated deleted-stub screenshot.

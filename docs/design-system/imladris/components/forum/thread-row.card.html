Both surfaces list topics and both link to the same /t/{id}-{slug}. What separates them is not the topic — it is whose state is on show. A board is the canonical index: one order, shared by everyone. An inbox is a working queue: assembled for one member, ordered by what needs them. The row is one structure with a presentation axis, exactly as the app's partials/thread_row.php has it.

The canonical index

/c/{slug} · presentation="board"

“What is in this board, and what moved most recently?” Pinned first, then last post — a fixed order every member sees. Activity goes to a right-hand rail so the titles form one scannable column.

    The personal queue

    /inbox · presentation="default"

    “What needs me?” Membership and order are per-viewer, so the row leads with the reason it is here, keeps activity inline, and can afford a snippet — you are reading rows, not scanning a column.

      Three classes of fact

      ClassFactsRule
      Topic-intrinsic author · title · status chips · pinned · locked · reply count · last activity Identical on both. These are properties of the topic, not of the person looking. If they read differently, the two surfaces are describing different objects.
      Viewer-relative unread dot · star · assigned to @ · snoozed until Renders on both — a topic you starred must read as starred on its own board. But it is the point of the queue and only a marker on the index: loud on one, quiet on the other.
      Surface-specific board label · snippet · queue reason Only where it answers that surface's question. A board does not label itself. A snippet is a triage aid, not an index entry. A board needs no reason to list its own topics.

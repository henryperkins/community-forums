## Summary

The largest measured delay is an oversized post image. On the mobile lab profile, the public thread `/t/1-this-is-a-topic` has **13.636 seconds LCP with an empty browser cache**, versus **1.356 seconds with the image cached**. Its 2,166,961-byte PNG is displayed only 279 CSS pixels wide. Transferring that image accounts for 10.846 seconds, or 79.54% of cold LCP; waiting for its response adds another 8.15%.

HTML remains sensitive to sequential database round trips. Five warm-container requests give **662 ms sample p75 for guest home** and **1,594 ms for the guest thread**, against the 800 ms target. Production SQL execution itself totals approximately 15 ms per home and 60 ms per thread. The database is still in GCP us-central1 and the running container is in ENAM, currently `ewr12`. Read-only provider evidence confirms both placements.

The first three actions are responsive image variants, an operator-led region-colocation rehearsal, and batching the member thread's unread-position queries where unread replies exist. A measured offline 640-pixel WebP variant is 37,432 bytes; the transfer-only estimate reduces cold **guest** thread LCP to about **2.99 seconds**, still above 2.5 seconds. Earlier discovery offers at most another 309 ms. Historical colocation timings imply another 0.7–1.0 seconds from guest HTML, making the combined changes plausible candidates for that target. The corresponding **staff** image-only estimate is still **5.10 seconds**; its larger HTML and image-response waits must also shrink. These are estimates requiring a deployed before/after replay, and unread-position batching offers no saving on the already-read production sample.

Guest-home mobile LCP was already **996 ms cold / 756 ms warm**. A subsequent user-authorized login enabled production measurements for an **administrator account**: home LCP was **1,736 / 1,300 ms**, and the image thread was **15,744 / 2,524 ms** with empty/repeated browser caches. The staff thread also exposed a **1.036996 repeat CLS**, split between late mobile-rail layout and editor-dock hydration. The historical colocation scenario alone still forecasts ordinary-member polls above 300 ms and the first member thread near 975 ms. It does not establish that every target will pass.

Five paced signed-in samples per route give **1,410 ms home / 2,472 ms already-read thread sample p75 HTML TTFB**. Presence and bell sample p75 are **620 / 830 ms**. Both HTML routes miss the 800 ms target, and every measured poll misses 300 ms. These staff results replace the authentication gap in the initial diagnosis; genuine first-unread production navigation remains unmeasured because both existing topics were already read.

This session used the default **diagnose** mode. It added evidence and diagnostic harnesses only. Application code, deployment, production configuration, database schema, runtime baselines, commits, and pushes were not changed. After the initial guest-only phase, the user supplied credentials and authorized sign-in. Authenticated measurement requests used GET/HEAD; the application performs its usual presence/session heartbeats and read-cursor persistence on these requests. No content, settings, or read-state reset was submitted. Credentials and cookies are excluded from saved evidence.
